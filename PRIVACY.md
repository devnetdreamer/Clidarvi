# Privacy and local data

This document describes the unmodified Clidarvi 0.1.0a1 first-party source and the exact CPython
3.13 dependency snapshot identified by `requirements-lock/runtime-py313.txt` and
`sbom/clidarvi-0.1.0a1.cdx.json`. It is not a promise about different dependency resolutions,
modified builds, third-party installers, package indexes, operating-system services, GitHub, or
later releases.

The local desktop application and voluntary project correspondence are different contexts. The
application behavior described below does not mean that visiting GitHub, opening an issue or pull
request, submitting a vulnerability report, or sending email is anonymous or local-only. Project
communications are described separately near the end of this notice.

## Scope of the no-telemetry statement

Clidarvi's first-party source does not intentionally implement an account system, advertising,
usage telemetry, analytics, crash reporting, cloud sync, or an automatic update checker. It does
not intentionally send inventory, site, credential, command, transcript, or risk-acknowledgement
data to the Clidarvi publisher or contributors.

The official CPython 3.13 installation procedure pins every package version in the complete runtime
dependency set and allowlists artifact SHA-256 hashes. Those hashes make an unexpected dependency
change detectable relative to that lock; the SBOM records the resolved composition and runtime-lock
fingerprint. A digest distributed with a file does not by itself authenticate the digest's
publisher. Neither hashes, an SBOM, an advisory scan, nor maintainer review proves that third-party
software has no defects, hidden behavior, telemetry, or future vulnerability. Third-party code runs
in the same process and can initiate its own operations. Users needing an enforceable network
boundary must apply operating-system or network egress controls and independently inspect the exact
artifacts they deploy.

Installing Clidarvi or its dependencies can contact a package index or another service selected by
the user's Python tooling. Git, an IDE, antivirus software, the operating system, DNS resolver,
firewall, proxy, certificate infrastructure, and backup or synchronization software can also make
connections independently of Clidarvi. Those services are outside Clidarvi's control.

## Expected application network traffic

The intended network operations in the unmodified first-party source occur only after a user starts
one of the following actions:

- DNS resolution through the operating system for a hostname entered in the inventory;
- TCP/SSH connections to the host and port selected by the user; and
- SSH host-key discovery for a device the user explicitly asks to verify.

After successful general-Automation authentication, pinned Netmiko can send platform-specific
session-preparation traffic before Clidarvi's reviewed command plan, including terminal-width,
paging, output-mode, privilege, mode-detection, or other state-changing operations. That hidden
traffic is generated by the selected driver and is not part of the visible command plan.

Aruba OS, Cisco WLC, and Fortinet can use a default-off Experimental Automation path only after the
operator explicitly enables it, selects exactly one target, and types
`RUN EXPERIMENTAL AUTOMATION` exactly in addition to all ordinary command-risk approvals. The
operator is responsible for ensuring the selected target is isolated and recoverable. Multiple or
mixed targets and a non-exact or cancelled confirmation are rejected before credentials or a
network connection. Before host-key lookup, credentials, or a new connection for this path,
Clidarvi reads local installed-distribution metadata and requires it to identify Netmiko exactly
as version 4.7.0. A missing or different version blocks Experimental Automation. The lookup is
local and does not contact a package index or update service. It is only a narrow version
boundary, not an integrity or behavior guarantee.

The experimental gate does not make driver setup observational or harmless. Clidarvi's
abort-oriented transport shutdown does not guarantee driver cleanup or restoration, especially
after an error, Stop, or another abort, so a pre-plan state change can persist.

Generic SSH (`generic`; shown as **Other** in the inventory editor) is rejected from general
Automation before credentials or network setup and remains Live-CLI-only. The
`ubiquiti_unifi_os` profile is also excluded from general Automation and can use only the
dedicated fixed-diagnostic path described below.

The separate experimental `ubiquiti_unifi_os` UDM observational-diagnostics path accepts one UDM
target and only the complete byte-for-byte preset `uptime`, `date -u`, `uname -a`, then `id`, in
that order. It rejects subsets, comments, blank lines, reordering, and extra text. For each preset
diagnostic it opens a Paramiko SSH exec channel without requesting a PTY or interactive shell, sends
the exact command, and receives stdout/stderr. It requests no environment and writes no remote stdin.
This first preview requires the console SSH account `root`. A command is bounded to 128 KiB of
stdout/stderr combined and 15 seconds; the complete run is bounded to 512 KiB. A fixed preset and
these bounds are scope controls, not proof of harmless or universally read-only behavior. The
device can update SSH/audit/accounting data and return hostnames, kernel/firmware details,
account/group information, time, uptime, error text, banners, or other confidential operational
data. Screen logs and an optional saved transcript may retain accepted stdout after best-effort
redaction. Unexpected stderr is received into bounded process memory and causes a fail-closed error;
its raw content is not intentionally added to the screen log or saved transcript. A presentation-only
device role does not alter this network behavior. See `README.md` and `docs/USER_GUIDE.md` for the
exact scope.

Before the first such operation, the official application requires the operational-risk
acknowledgement described in [TERMS.md](TERMS.md). Acceptance is recorded locally; it is not sent to
the Clidarvi publisher by the application.

## Data stored on the computer

Clidarvi may store:

- `devices.json`: device display names, hostnames or IP addresses, ports, vendor/device profiles,
  presentation-only device roles, stable random IDs, folder structure, and optional physical-site
  details;
- `devices.json.bak` and timestamped corrupt copies used for recovery;
- `known_hosts`: SSH public host keys accepted by the user;
- `clidarvi.lock`: a normally transient Qt single-instance lock containing lock metadata such as
  the process ID, local hostname, and application name. It is normally removed on clean shutdown
  but can remain stale after a crash or forced termination;
- `risk-acknowledgement.json`: acknowledgement schema and terms identifiers, Clidarvi version,
  accepted acknowledgement-item identifiers, acceptance time in UTC, the legal-bundle SHA-256,
  individual document SHA-256 values, the required runtime dependency-snapshot identifier, and an
  `installed_runtime_verified` flag that is always `false` in this version; and
- optional command transcripts in `outputs/` or another location selected by the user.

The user can also choose paths outside the application-data directory for inventory exports,
command transcripts, or a retained copy of the acknowledged terms. Those files are local but are
not deleted when the application-data directory is removed.

The risk-acknowledgement record is designed not to contain a name, username, email address,
credential, device hostname, device address, command, IP address, or hardware identifier. It shows
only that the acknowledgement controls were completed on that local installation; it does not
prove the real-world identity, authority, or understanding of the person who clicked them.

The acknowledgement hashes bundled documents and the runtime lock. It does not hash the running
application, attest its origin, inventory installed packages, or establish that the environment
actually matches the lock.

Physical-site fields can contain addresses, location details, access instructions, and notes.
Inventory exports include those fields. Logs and transcripts can contain device names, addresses,
configuration state, usernames echoed by a device, or other confidential information even after
best-effort secret redaction.

On platforms that support Unix-style permissions, Clidarvi requests private permissions for its
application-data directory and sensitive files. Operating-system policy, backups, synchronization
tools, administrators, malware, or a modified build can still make data accessible. Clidarvi does
not encrypt inventory, site details, known-host files, acknowledgement records, or transcripts at
rest.

## Credentials

Usernames and passwords are requested when a connection is started. They are not intentionally
written to the inventory or another Clidarvi data file. Mutable password buffers are overwritten
on a best-effort basis, but Python, Qt, Paramiko, Netmiko, and the operating system can create
immutable or internal copies. Clidarvi therefore cannot guarantee physical memory erasure. Use a
dedicated, least-privileged account and prefer short-lived credentials where supported. The first
experimental UDM diagnostics preview is an explicit exception: it accepts only the privileged
UniFi OS console SSH account `root`, so use it only on an isolated/recoverable authorized target.

Both automation and Live CLI require a password in this alpha. In Live CLI, host-key discovery and
verification occur before the credential prompt, so the selected device may already have received
DNS/TCP/SSH-preauthentication traffic. Submitting an empty password then cancels session
authentication before an `InteractiveSSHWorker` starts. SSH-agent and default-private-key discovery
are explicitly disabled. This restriction avoids an RSA-certificate/SHA-1 path in the pinned
Paramiko 4 dependency. It is a scoped mitigation rather than an upstream patch and may be
reconsidered only after Clidarvi can use and test a dependency revision that no longer contains the
affected code.

Never put credentials, private keys, recovery codes, community strings, or tokens in site notes,
device labels, commands, issue reports, or transcripts.

## Local files read by the application

Depending on the action selected, Clidarvi reads only local files needed for that action:

- in a source checkout, a bounded `pyproject.toml` is read to recognize the checkout before the
  requested bundled legal notice, runtime lock, logo, field-test document, inventory icon, or SBOM
  is read for the selected application view;
- in an installed wheel, the imported `clidarvi.py` plus adjacent `METADATA` and `RECORD` are read
  and hash-checked, followed by the complete fixed 31-file runtime bundle, whenever a bundled asset
  is resolved. This binds the legal notices, runtime lock, logo, field-test checklist, inventory
  icons, and SBOM to one coherent wheel `RECORD` and installation layout before the requested asset
  is used;
- `devices.json`, its backup/recovery copies, `risk-acknowledgement.json`, Clidarvi's `known_hosts`
  file, and `clidarvi.lock` for single-instance coordination in the application-data directory;
- a JSON or XML inventory file explicitly selected by the user for import.

The official application uses only keys approved through Clidarvi's own host-key flow. Automation
uses Clidarvi's `known_hosts` file, while Live CLI pins the exact key returned by the immediately
preceding background verification in memory. It does not import trust from the user's or operating
system's SSH known-host stores.

The application does not parse or transmit the SBOM. In an installed wheel it reads and hashes
the SBOM's raw bytes only as part of the local bundle-integrity check described above; the SBOM is
otherwise included for manual inspection and release verification.

Clidarvi also obtains ordinary local path, platform, environment, and package-installation
locations to find its application-data directory and bundled assets. Importing, exporting, saving
a transcript, or retaining a terms copy requires the user to choose or confirm the relevant file
path. These reads are local first-party behavior; operating-system services, endpoint security,
backup/sync tools, Python tooling, or third-party libraries can separately observe or process file
access.

## Storage locations and deletion

The default application-data directory is:

- macOS: `~/Library/Application Support/Clidarvi/`
- Windows: `%APPDATA%\Clidarvi\`
- Linux: `$XDG_DATA_HOME/Clidarvi/` or `~/.local/share/Clidarvi/`

Clidarvi does not automatically expire stored records. To remove local application data, close all
Clidarvi instances, verify any backups you intend to retain, and delete the `Clidarvi` directory
shown above, including any stale `clidarvi.lock` after every Clidarvi instance is closed.
Separately remove exports or transcripts saved elsewhere. Deleting `risk-acknowledgement.json`
causes the official application to request acknowledgement again before
a network operation, except in a running instance that already verified the record during its
current session; that instance re-checks at its next start. Copies may remain in system backups,
version-control history, cloud-sync services, logs, forensic storage, or recipient systems.

## User responsibility

The person or organization operating Clidarvi decides what data to enter, which devices to contact,
how long to retain files, and with whom to share exports. That operator is responsible for lawful
processing, access control, retention, and deletion under the rules that apply to them.

identify the published project channels, but control of them does not verify a real-world legal

jurisdiction-specific controller-identification or transparency duty. Mandatory law may require a

When someone views or interacts with the GitHub repository, GitHub may process account/profile
details, IP/device and access information, cookies, and repository activity under GitHub's own
terms and privacy practices. Material intentionally submitted through an issue, discussion, pull
request, review, commit, or other public repository feature can expose the submitter's handle,
profile, commit identity, timestamps, content, and attachments publicly. Maintainers may receive
copies or notifications and use the submitted information to administer the project, review
contributions, investigate reports, prevent abuse, and reply. Public content can persist in Git

Messages voluntarily sent to `info@clidarvi.io`, `privacy@clidarvi.io`, or

Ordinary internet email is not guaranteed to be end-to-end encrypted. Provider logs, backups,
spam/security systems, legal obligations, public Git history, and third-party copies are outside
the application's control, so this notice promises no fixed correspondence-retention period or

Do not submit credentials, private keys, recovery codes, personal, confidential, or production
data, raw configurations, host keys, or sensitive transcripts. Use sanitized reproductions, RFC
documentation addresses, and fake credentials. Questions about this privacy notice may be sent to
